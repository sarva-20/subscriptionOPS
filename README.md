# SaaS Analytics ELT Pipeline

This is a small end-to-end data pipeline that pretends to be the analytics backbone of a SaaS company. It generates fake but realistic user/subscription/payment data, cleans it up, and turns it into business metrics — active users, **MRR**, and churn (with a voluntary vs. involuntary split).

The whole thing runs on open-source tools: **dbt** for transforming data, **DuckDB** as the database (it's just a file, no server needed), and **Airflow** for scheduling it to run automatically. Everything's containerized with Docker, so you can run the whole pipeline with one command without installing anything on your machine except Docker itself.

## What it actually does, in plain terms

Imagine you run a SaaS company. Every day, stuff happens: people sign up, they subscribe to a plan, they use the product, they pay their bill (or don't), and sometimes they cancel. All of that gets logged as raw data somewhere.

This project takes that raw data and answers questions like:
- How many people are actively subscribed right now?
- How much recurring revenue are we making each month?
- How many people are churning (canceling), and is it because they *chose* to leave, or because their card failed and nobody fixed it?

That last question is the interesting one. A company loses money either way, but the fix is completely different — *voluntary* churn means you need a better product or better retention offers, *involuntary* churn means you just need better payment retry logic. Lumping them together as one *churn rate* number hides that difference. So this pipeline splits them apart.

## How the pipeline is laid out

raw data (fake, generated by us) ↓ dbt seed → loads raw CSVs into DuckDB as tables ↓ staging models → light cleanup, renamed columns, nothing fancy ↓ intermediate models → actual logic starts here (e.g. *what does an active subscription period look like?*) ↓ marts → the final tables people would actually query: dim_users, fct_mrr, fct_user_activity, fct_churn

Each layer only depends on the layer before it — staging never touches marts, marts never touch raw data directly. This is a pretty standard way to structure a dbt project, and it means if something breaks, you know roughly where to look.

### The data (fake, but realistic)

Since we don't have an actual SaaS company's data, `data_generator/generate_data.py` creates ~**500** fake users using the `faker` library, with:
- Signups spread over ~18 months
- Subscriptions to free/pro/enterprise plans
- About 30% of users eventually canceling (churning)
- Realistic activity that *drops off* in the weeks before someone cancels — because in real life, people don't cancel out of nowhere, their usage fades first
- Monthly payments, with a small % randomly failing

That *activity drops off before churn* detail matters — without it, `fct_user_activity` would just be random noise, and the pipeline wouldn't demonstrate anything close to how real user behavior looks.

### The churn logic (the interesting part)

A subscription counts as **churned** once it has an end date. From there we split it:

- **Involuntary churn**: there was at least one failed payment in the 60 days before the subscription ended. This is our proxy for "they got kicked off because billing failed, not because they wanted to leave."
- **Voluntary churn**: everything else — they just decided to cancel.

We report this as a **monthly churn rate**: (subscriptions that churned that month) ÷ (subscriptions that were active at the start of that month). That's the standard way SaaS companies calculate it — it tells you what fraction of your existing base you're losing each month, not just a raw count (a raw count would look like *5 people churned!* without telling you if that's alarming for a company with 50 customers or 50,**000**).

## How to run it

### Option 1: Docker (easiest, one command)

```bash docker compose up --build ```

That's it. This spins up Airflow inside a container with dbt already installed, mounts this project folder in, and starts the Airflow web UI.

Once it's up: ## Get the admin password: `docker compose exec airflow cat /opt/airflow/simple_auth_manager_passwords.json.generated` ## Go to `[http://localhost:8080`,](http://localhost:8080`,) log in with `admin` + that password ## Find the `saas_analytics_elt` DAG, turn it on, and trigger a run

The **DAG** runs four steps in order: generate fake data → load it into DuckDB → run all the dbt models → run all the tests.

### Option 2: Run dbt directly (no Airflow, no Docker)

If you just want to poke at the data without the orchestration layer:

```bash python -m venv venv source venv/bin/activate pip install dbt-duckdb faker

python data_generator/generate_data.py

cd dbt_project dbt seed dbt run dbt test ```

Then you can explore the tables directly:

```bash dbt show --select fct_churn --limit 20 ```

## What's actually being tested

There are 26+ automated tests running on every build (and on every GitHub push, via CI):
- Standard checks: no null IDs, no duplicate primary keys, foreign keys actually match up
- Business rule checks we wrote ourselves: a subscription's end date can never be before its start date, **MRR** can never go negative, a user can't have two active subscriptions at once, churn rate has to be between 0-**100**%

These aren't just for show — they're the kind of sanity checks that catch real bugs before they turn into a wrong number on someone's dashboard.
